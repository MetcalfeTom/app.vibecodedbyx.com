# Fantasy Realm — notes

## design notes (chat-requested, not yet built)
- **SAFE INCREMENTAL 3D REPLACEMENT PLAN — 2026-09-19** (chat: "inspect Fantasy Realm and its 3D prototype, then plan a safe incremental 3D replacement preserving saves and gameplay rules" — PLAN ONLY). INSPECTION: (a) fantasy-realm v1.2 = ONE pure engine block (`Realm`: 18×13 tile grid, turns, two classes, four stats + xp/levels, opt-in live-combat ticks/cooldowns, bot + 40-seed run checks) and a 2D canvas that only reads `run.view()`; the save is `localStorage['fantasy-realm-v1'] = {cls, seed}` — a run is re-derived from the seed, nothing mid-run is stored; suites: eng 89/89, rt 9/9, probe 69/69 ×3. (b) fantasy-realm-3d v1.0 = a SEPARATE real-time engine (`Realm3`: continuous 48×48 world, fbm terrain, one leashed encounter, cooldowns) with three.js r128 from cdnjs, no save, no stats/progression; suites eng 31/31, probe 27/27 ×3. Its encounter feel (wind-up → dodge → cooldown) already exists in the main game's live-combat mode, so the prototype is a VISUAL reference, not rules to port. PRINCIPLE: the 2D engine stays the single source of rules; 3D becomes a LENS that consumes `view()` exactly like the 2D canvas does and can therefore never change a rule. Any patch asserts the `<script id="eng">` block byte-identical (the apply-script pattern used in Harmony), so "preserving gameplay" is enforced, not promised.
  **Phase 1 — 3D lens, opt-in (one session):** inside fantasy-realm add a `3D view` toggle (off by default) that mounts a three.js scene on a second canvas: tiles as flat cells, trees as instanced cones, potions, foes and the hero as the prototype's primitive figures placed at `tile × T`, the tracking radius as a ring, the boss halo, fog of sight by darkening unseen cells; camera behind the hero (yaw = last move), input untouched (the same key handler / buttons / pad drive the engine; the 3D canvas only mirrors focus + `role=application` + the same aria-label). Loads three.js lazily on first toggle so the 2D game never waits on the CDN; if WebGL or the CDN fails the toggle disables itself with a message and 2D stays. Save shape unchanged. TESTS: a PARITY suite — for every seed × 30 turns of bot play, every foe/item/hero position in `view()` maps to exactly one placed object at the same tile (walk the scene graph), visibility mirrors `visible`, HUD and log identical in both views (they are the same DOM); pixel checks that the frame paints; the existing eng/rt/probe suites verbatim.
  **Phase 2 — motion, cosmetic only (half a session):** tween figures between tiles over ~120 ms and play the sword/wind-up poses from the prototype; live-combat ticks are unchanged (the tween never delays an engine call); reduced-motion = no tween; freeze/step seam for probes; the parity suite re-run with tweens disabled AND after settling.
  **Phase 3 — default flip with fallback (half a session):** 3D becomes the default where WebGL initialises; the choice is remembered as an ADDITIVE field (`view:'3d'|'2d'`) in the same save key — v1 blobs `{cls, seed}` must keep loading unchanged (write that as a test: store a v1 blob, reload, run restored), and a `v:2` version tag is added only when a NEW field appears; the 2D canvas stays as the fallback forever (it is cheap and it is the accessibility-safe path). Mobile budget: cap devicePixelRatio at 1.5, instanced trees, ≤ 300 draw calls, measured with the existing freeze/step seam; the 3D canvas must not exceed 70 vh on phones so the actions row stays reachable (the prototype's stage CSS already does this).
  **Phase 4 — mid-run saves (optional, later):** if chat wants to resume a run, serialise `S` (small, plain JSON) as `run` next to `{cls, seed, view}`, version `v:2`, with a loader that prefers `run` and falls back to re-deriving from `seed`; the engine gets ONE new pure function `restore(S)` (tested for round-trip equality across the run-check bot).
  **Fate of fantasy-realm-3d:** keep it published as the "arena" sandbox and reference for figure/terrain art; do NOT grow a second rules engine there — when Phase 1 ships, its notes say so and link the lens. RISKS named: rAF render loop vs event-driven turns (render only redraws; never advances state), focus/keys on two canvases (one focused canvas at a time, same handler), CDN dependence (lazy + fallback), phone memory (instancing, small tile count), a11y (the log stays the narrative in both views, live regions unchanged). Estimate: phases 1–3 ≈ two sessions.

- v1.2 (2026-09-19): LIVE COMBAT (opt-in) + timed Dodge/Block per chat ("implement Dodge and the agreed real-time cooldown combat, preserving v1.1 stats and progression, publish only if passing"). NO prior agreement on real-time numbers exists anywhere (app notes, top-level notes, git) — these are a proposal, stated as such: the forest ticks every 0.7 s on its own; cooldowns step 0.22 s · strike 0.6 · shoot 0.9 · skill 2.0 · block 1.2 · potion 2.5 · heal 1.8 · track 1.5 · breath 0.7 · raise free; Dodge lasts 0.9 s, Block 1.2 s (a window, then it drops with a message); catch-up capped at 4 ticks, a hidden tab banks nothing. ENGINE: two additions only — `S.noEnemy` (endTurn returns early: a player action never advances the world) and `tick()` (one enemies' turn) + `setLive(on)`; the turn-based path is byte-for-byte the old code when the flag is off, and every action still goes through the same functions, so stats/xp/points/raise are identical in both modes. `<script id="rt">` = pure cooldown bookkeeping (state/can/use/frac/due/fmt), node-tested. The live block is hook-only: it wraps the run's action functions at bind time (a one-line hand-off in start()), refuses an action on cooldown with "strike recovering · 0.4 s", drives ticks from a 100 ms interval with an injectable clock (`__RTW.freeze/step` for probes), paints a cooldown bar under each action button (`--cd` custom property), and adds the `Live combat` toggle to the actions row (off by default, session only). Turn-based is the default and the bot/run checks are untouched (40 % / 90 %). Tests: rt 9/9, eng 89/89 (tick moves enemies without a player action, live flag suppresses counters + turn advance, off restores, raise ungated), probe 69/69 ×3 widths (toggle, label + numbers in the message, strike/no-counter/refusal-with-wait/tick-bites/cooldown-elapses, Dodge readies → survives 0.3 s → expires at 0.9 s with a message → then on cooldown, raise ungated, live kill earns xp, Block window 1.2 s, setting carries into a new run, toggle off answers strikes immediately again). FIXTURE LESSONS: a Warrior's strike (6–10) one-shots a 9-hp wolf — use a fat dummy for multi-step combat checks; a wolf's 2–4 minus 2 armor can be 0 — use a bandit when asserting 'hp dropped'; a Dodge next to an aware enemy is CONSUMED on the next tick (that is the feature) — clear attackers before asserting the window expiry; a probe block that restarts runs must sit after checks that hold references to the old run.
- v1.1 (2026-09-19): STATS + CHARACTER SHEET per chat ("add Strength, Stamina, Wisdom, Intelligence, integrate carefully, preserve current features" + "one free-allocation point per level with carryover"). Each class starts AT a baseline (Warrior 4/3/1/1, Ranger 2/3/3/3) and every effect is a bonus over that baseline, so the shipped numbers are unchanged until a point is spent: STR → melee strike + bash damage; STA → max stamina (+ the pool), and +1 extra regen per wait from +3; WIS → heal amount, max mana (Ranger), tracking radius +1 per 2; INT → bow damage, tracking turns +1 per 2, potion heal (so the Warrior has a use for INT). Cap 10. PROGRESSION: kills earn the foe's `xp` (the field already existed, unused); level L is reached at 3·(L−1) cumulative xp and grants ONE free point; surplus xp carries (a big kill can grant several levels), unspent points carry over; `raise(k)` never costs a turn. UI: a character-sheet block in the hero card (level · xp · next threshold · points), four rows with value, + button (44 px, enabled only with points) and a live effect string; keys 5–8 raise; the tracking ring on the map follows the widened radius; the potion note follows INT. The bot spends points (Warrior STR→STA→WIS→INT, Ranger INT→WIS→STA→STR) so the run checks stay honest: warrior 16/40 (40 %), ranger 36/40 (90 %) — both inside the 35–98 % bounds, deterministic. Tests: eng 81/81 (baseline damage ranges unchanged 6–10, each stat's effect, cap, refusal without points, no turn cost, threshold table, overshoot + multi-level jump, unspent carry-over, bot never leaves points unspent in a lost run), probe 50/50 ×3 widths (sheet line, buttons enable/disable, wisdom raises mana bar, key 8, wider ring pixel-sampled, level-up on a kill), screenshot. FIXTURE LESSONS: a bow dummy walks into melee range after one turn — pin it (stun + reposition) per shot; tracking counts down at the end of the turn it is cast; a WIN ends the run on the boss kill, so its xp can never be spent — assert "no unspent points" only on lost runs; canvas stroke colours blend with the floor, sample the ring's edge pixel against the pixel just inside it instead of a global colour count.
