- **MIX REHEARSAL (DRY-RUN) WINDOW INSPECTION — 2026-09-20** (chat: "inspect Harmony's mix rehearsal window logic, report the exact missing behavior, make no unrelated changes" — READ-ONLY, no code touched). What exists: `#adjdry` → `dryRun()` (index.html ~3304) rides a ghost fader over the dual-wave preview for a FIXED 5000 ms, calling `drawPreview(pr)` every 50 ms; `drawPreview` (~3258) shades A's window at `plan.outStart … +plan.dur` and B's at `plan.inStart … +plan.dur`, draws the curve in force for A's track (`rideCurve(cp.a.k)`), the tail/head handles and the ghost-fader readout; `currentPlan()` (~3253) = `planTransition(deckInfo(A), deckInfo(B))`. Provably inert (adj spy suite) — by design, not a gap. EXACT MISSING BEHAVIOUR vs the live hand-off it claims to rehearse: (1) DIRECTION — the rehearsal is hard-wired A→B (`currentPlan` always plans a→b, status text says "on A into B", A is always shaded as outgoing, A's curve is always the one drawn); `liveRun` picks the OUTGOING deck from playing state (fader breaks a both-playing tie), so with B playing the rehearsal shows the wrong direction and the wrong curve. (2) TIME BASE — 5000 ms flat vs the live ride's `plan.dur × 1000` (8 bars ≈ 15 s at 128 bpm), so the ghost-fader % is not the real pace and bars are not counted. (3) SYNC-FIRST NOT REHEARSED — the live path tempo-locks, WAITS for the outgoing deck's next bar line (or, since v4.15, its loop wrap), keeps the fader parked (`drawPreview(0)` while `LIVE.pending`), then settles + verifies; the dry run starts the ride at the press instant with no pending phase, no bar-line countdown, no loop-wrap case. (4) START POINT — the live mix (manual ⚡) starts from wherever the outgoing deck IS NOW; the rehearsal is anchored at `plan.outStart`, which is the CHAIN's planned mix-out, so "what happens if I press ⚡ now" is never shown. (5) INCOMING WINDOW SCALE — B's shaded span is `p.dur / b.dur` in B's own seconds, but `p.dur` is measured in A-track seconds at A's rate; at a synced rate B's window should be `p.dur × (rateB/rateA)` of B's timeline (a few % off for a 4–6 % pitch). Minor: a cue edit mid-rehearsal moves the window under the ghost fader (the plan is recomputed every tick), and a gridless pair still gets bar-shaped windows. Smallest honest fix, if asked: give `currentPlan()` an outgoing letter (the playing deck, else A), let `dryRun` take `T = plan.dur × 1000` with a "waiting for the bar line" lead equal to `syncFirstSchedule(...).waitSec` drawn as a parked fader, and scale B's window by the rate ratio — all display-only, timing block untouched.

- **v4.9 DESIGN — hybrid curve editing + safe pool fallback after setlist exhaustion — 2026-09-17** (chat: "Design Harmony 4.9 with hybrid curve editing and safe AutoDJ fallback to the main pool after setlist exhaustion, preserving intentional stops" — DESIGN ONLY, nothing built; grounded in shipped v4.8). WHAT EXISTS: the auto-mix ride is ONE fixed shape — liveTick moves the fader linearly from `from` to `to` over `durMs` and applyXf maps position → (cos, sin) equal-power gains; the manual fader uses the same mapping. The chain (v4.2) picks the next ELIGIBLE setlist track after each hand-off; when nothing is eligible it says "setlist exhausted — deck plays out" and re-looks every 3 s (setlist edits revive it). ⏹ / any touch → takeover → chainOff; "waiting for exactly one playing deck" already forbids starting from silence.
  **1) Hybrid curve = a pure `curveAt(t, spec)` beside equalPower, never inside the scheduler.** `spec = { mix: 0..1, tailOut: 0..0.5, headIn: 0..0.5 }`: mix blends equal-power (0) ↔ a steep "cut" sigmoid (1); tailOut holds the OUTGOING at full gain for the first tailOut of the window before it falls; headIn brings the INCOMING to full by (1 − headIn) — that asymmetry is the "hybrid" DJ ask (fast cut out, gentle blend in, or the reverse). INVARIANTS the node suite enforces: mix=0, tails=0 reproduces equalPower(t) to 1e-12 (preservation by construction); a(0)=1,b(0)=0,a(1)=0,b(1)=1 exactly; both gains monotonic; summed power a²+b² ≤ 1.12 (≈+0.5 dB) at every t — a hybrid may not go louder than the equal-power crossover by more than that, so the guard NORMALISES rather than clips. The ride keeps its clock: liveTick still computes t from LIVE.t0/durMs (v4.7 A untouched) but sets deck gains DIRECTLY via decks.X.setXf(a/b) and parks the fader thumb at the equivalent position atan2(b,a)/(π/2) for display, still under `injecting` so takeover keeps working. MANUAL fader stays equal-power (no change). Spec lives per transition pair in the mixcues store (`cues[key].curve`), default = equal-power; a "reset to equal-power" chip clears it.
  **2) Editing surface = the existing dual-wave preview (#adjwave).** Three handles drawn over the shaded window: a MIX knob (drag up/down anywhere in the window), a TAIL handle on the outgoing lane (drag horizontally, snapped to whole beats of the OUTGOING grid), a HEAD handle on the incoming lane (snapped to the incoming grid). 44 px hit targets, keyboard: arrow keys nudge the focused handle one beat / 5 % mix, Escape reverts the drag. The curve is redrawn live (the preview already paints the equal-power lines each frame); a text readout under it says the spec in words ("cut-leaning 60 % · outgoing holds 2 beats · incoming full 1 beat early"). Dry-run (ghost fader) uses the same curveAt so the 5 s rehearsal shows the edited shape before anything plays.
  **3) Pool fallback = a THIRD chain tier, opt-in, never implied.** The chain button cycles off → "setlist" (today, unchanged) → "setlist → pool". In the pool tier chainPick runs exactly as now first; ONLY when the setlist yields nothing does `poolPick(liveRec)` run: candidates = crate rows ranked by the existing match.js score against the LIVE deck's effective bpm + key, filtered by the same chainEligible rules (present, not played tonight, not the live track, not a flagged duplicate, no fingerprint of anything played) PLUS "not passed over tonight" (see 4), and require score ≥ 50 (match.js "playable" floor) — below that the deck plays out exactly as today, with the reason in the explainer. Tie-break deterministic: higher score, then older `added`. The pick is APPENDED to the setlist as a ghost "auto" entry (visible in the drawer, removable) before it loads, so the DJ sees what is coming and can veto it; removing it disarms and re-picks.
  **4) Intentional stops preserved — the rules, each with a test:** (a) ⏹ or any manual touch mid-mix → takeover → chainOff, both tiers, unchanged (existing chain suite pins it). (b) Two silent decks → nothing is ever started, both tiers (existing "exactly one playing deck" rule; new probe: pool tier + two stopped decks + 12 s → zero play calls via the Deck spy). (c) A manual STOP/PAUSE of the live deck while armed → chain waits (today's behaviour), the pool tier does not treat that as exhaustion. (d) A setlist ✕ during the session marks that id "passed over tonight" (session memory, not persisted) — the pool never resurrects a track the DJ explicitly removed. (e) A refused liveRun (duplicate block, no plan) still switches the chain OFF rather than trying the next pool candidate — no silent hunting; the DJ re-arms deliberately. (f) The tier persists only for the session (boot = off, as today). (g) Setlist additions always win: the 3-s re-look checks the setlist first even while a pool pick is loading (a pending pool load is dropped if a setlist track becomes eligible before it fires).
  **5) Timing code: untouched.** liveRun / syncFirstSchedule / fireLive / settle+verify / CHAIN_LEAD / tolerance stay byte-identical (apply script asserts the block, as v4.8 did, with only liveTick's gain line and the chain pick delegated to new functions outside the guarded region). Preservation battery = every suite verbatim: chain 35, live 24, sync 23, quant 16, gridless 20, edit 32, pool 14, setlist 48, sched 18, baroff 12.
  **6) Proposed tests written BEFORE code:** node `curve.test.js` (identity-to-equalPower, endpoints, monotonic, power bound across a 41×11×11 grid of t/mix/tails, snapping to beats), node `poolpick.test.js` (setlist-first, threshold, eligibility incl. passed-over, tie-break, exhaustion → null), browser `curve-tail` (drag/keyboard handles, per-pair persistence, dry-run uses the shape, mid-ride gains match curveAt(t) within the 50 ms tick, takeover during a hybrid ride), browser `pool-tail` (exhaustion → pool arm with ghost row → hand-off on the planned bar line via the same residual ±40 ms check; ⏹ → off and 10 s of silence; two silent decks → nothing; passed-over exclusion; setlist edit wins over a pending pool pick).
  **7) Slices:** 4.9a = pool tier (chainPick delegation + tier button + ghost row + explainer, ~half a session), 4.9b = curve editing (pure curve + preview handles + ride gain path, ~one session). Recommend 4.9a first: it reuses every rail and has the clearer test surface.

## issues
- cueSet rounds to 10 ms — any "moved by exactly one bar" assert needs a ≥ 11 ms tolerance.
- A synthetic beat track suggests only one or two phrase markers — add markers with phadd before testing multi-step deletes.
- "Quarter-bar drift" reports: check the DIAG report first (X.diagReport()) — if barJumps is 0 and the offset histogram has one key, it is a constant manual-sync bar offset, not drift; the readout now names it. Ground-truth alignment tests need fixtures with the accent OFF slot 0, or a downbeat-index bug can never show.
- `d.grid === null` means BOTH "still scanning" and "scan finished, no usable grid" — any wait-for-analysis loop must key on `scanDone`, never on the grid.
- Probe fixtures: after loadFile() the OLD deck fields linger until decode lands — wait on d.name/d.buffer/scanDone, not on a flag that was already true; ⚡ is re-enabled by renderCues every 1.2 s, so wait for !disabled before clicking; a chained completion overwrites "hand-off complete" with the chain's next note — assert on deck/fader state instead.
- `grid.downbeat` is a beat INDEX (0–3), not seconds — anything that anchors bars must go through barAnchor(). The old planner test fixture (`downbeat: 0.2`) encoded the misreading; barAnchor keeps it as seconds so that fixture still passes.
- Media-element start latency is real (≈150 ms here): never assume play() puts the clock where you seeked — measure after the clock advances and correct while the deck is still silent.
- Bar-alignment probes must use the SAME anchor as the code (barAnchor) — measuring bars from t=0 while beats lock to beat0 reads as a 0.45-beat "misalignment" that isn't one.
- Chain suite fixture lessons (+): click ⚡ only after the panel enables it (renderCues runs every 1.2 s); when the paused deck already holds an eligible track the chain must NOT reload it — assert on chain.nextId, not on a new load; reset the played list BEFORE toggling the chain on or it picks a different track; a fifth header button overflowed phones only — compare scrollWidth against the unpatched baseline before blaming a change.
- Crate: `pump()`'s drain branch used to `status('')` unconditionally — any message set while the queue was idle (dup skipped, adoption) was wiped the same tick it appeared, because importFiles always ends with `pump()`. Now it only clears when the current status carries the `busy` class. Lesson: a cleanup that resets shared UI state must check it still owns that state.
- Crate: `<option>` text collapses whitespace — playlist tree indentation uses figure spaces ( ), not plain spaces.
- Crate: `.next{display:grid}` / `.btn{display:inline-flex}` silently beat the `hidden` attribute — the empty crate showed a phantom "NEXT UP → B" strip while the probe's `.hidden` property check passed. Fixed with `#crate [hidden]{display:none!important}`; probes now assert `getComputedStyle(...).display`, not the property.
- Crate: `added` stamps must be unique — 4 files imported in one `importFiles` call shared a millisecond and "newest first" tied (fixed with a monotonic `stamp()`).
- Crate: loading from the crate still re-runs the deck's own analysis (setBuffer's contract) — harmless (~1.6 s/30 s in a worker) but a `meta` argument on setBuffer would skip it.
- Crate: "next for · auto" follows the LAST LOADED deck when nothing is playing, so right after loading the suggestion into B the reference flips to B — intended (B is what you'll play next), but it surprises a probe that expects A.
- Key detection on very sparse synthetic material can land on a neighbour (a D-major triad + 70 Hz kick read as F♯ minor); the crate stores whatever the deck/worker said and lets you ✎ fix it.
- Pitch is plain resampling (playbackRate), so ±8 % shifts the key ≈ ±1.3 semitones — deliberate vinyl feel; the key badge shows the analysed (0 %) key.
- Key confidence < .25 shows a "?" after the key name. Sparse / drone-y material and DnB half-time will occasionally read an octave/relative off.
- Analysis takes ~1.6 s per 30 s of audio in the worker (≈ 15 s for a 5-minute track); the wave shows "reading bpm + key…" meanwhile and the deck already plays.
- Headless testing: an `await` on a worker with no pending timers makes `--virtual-time-budget` jump to its deadline before the worker replies — use the real-time hold/release harness (pending `<img src=/_t/hold>` blocks `load`; the tail fetches `/_t/release` when done) in the job tmp.
